# Assumptions

Running list; referenced in the interview.

- USD only (single currency).
- PO amounts are pre-tax; invoices are compared to PO on **subtotal**.
- Held invoices do **not** consume PO balance (only APPROVE does).
- Price tolerance is 2% over the PO (remaining balance, and per-line unit price).
- Demo tax rate is 10%, shown separately unless a sample says otherwise.
- Inferred POs (invoice has no PO reference) always require a human to confirm.
- Security flags always HOLD. A security-flagged run can never be APPROVE.
- Demo has no user auth (single tenant). The reset endpoint is token-guarded.
- Bank details are only ever taken from the vendor master; the invoice's bank account is only compared.
- Runs are append-only; re-processing creates a new run.

## Deviations from the plan

(Add an entry here whenever the implementation deliberately differs from IMPLEMENTATION_PLAN.md, with the reason.)

- Project lives in `asa-case-study/` under the workspace root.
- No OpenRouter key was available in the build environment, so live extraction could not be run during the build. An offline **mock extractor** (`EXTRACT_MOCK=1`, truth-JSON driven) exists purely so the pipeline/UI can be exercised end to end; it is never the default and the run's `model` column shows `mock`.
- Railway deploy could not be executed from the build environment; deploy config + instructions are prepared instead.
- Phase 0: `.gitignore` also has `!.env.example` after `.env*` so the example env file stays tracked (the plan only says to ignore `.env*`). It also ignores `data/app.db-*` (SQLite WAL/SHM files) and keeps `data/uploads/.gitkeep`.
- Phase 0: create-next-app refuses a non-empty directory, so it was run in a scratch dir and the files moved in (no existing file overwritten). Scaffolded with `--no-turbopack` (plain webpack `next dev` / `next build`).
- Phase 0: the current shadcn CLI (4.x) was initialised with `--base radix --preset nova` (style `radix-nova`, neutral base colour, lucide icons). It writes `src/lib/utils.ts` as `export { cn } from "cn"` and adds the `cn` npm package (maintained by shadcn, repo shadcn-ui/cn) instead of `clsx` + `tailwind-merge`. Left as generated.
- Phase 0: the Geist font CSS variable in `src/app/layout.tsx` was renamed from `--font-geist-sans` to `--font-sans`, because the generated `globals.css` maps `--font-sans: var(--font-sans)` and would otherwise be self-referential.
- Phase 0: `unpdf` and `pdf-lib` do not need `serverExternalPackages`; a throwaway route importing both plus `better-sqlite3` built and ran under `next start`. Only `better-sqlite3` is listed.
- Contracts: `suspicious_content` items may be up to 500 characters (max 20 items) instead of the general 200-character string limit, so a verbatim quote of an injection (sample #9's is about 190 characters) never turns into "invalid output" and loses the evidence.
- Contracts: a confidence outside 0..1 is invalid output (retry, then fallback); the plan's "clamped" is read as "bounded". Clamping would silently turn a percentage like 85 into 1.0 and weaken the low-confidence check.
- Contracts: `decide()` treats a `warn` with severity `hold` as HOLD. The plan lists the inferred PO (stage 7) as a warning that HOLDs, but its precedence list only mentions fails; this reconciles the two.
- Contracts: decision reasons are ordered decisive first (reject, then hold/error, then info notes), stage order within each group, so `reasons[0]` (the dashboard's top reason) explains the decision, e.g. the duplicate for #4 rather than the PO balance.
- Contracts: each pre-loaded history invoice gets a synthetic `done` run (model `history`, deterministic RFC 9562 UUID, no steps) so dashboard rows link to a run view; `invoices.id` equals the run id for every row.
- Contracts: a run interrupted by a restart keeps `decision` NULL (it never decided); its running step becomes `error` and its pending steps `skipped`. It writes no invoices row, so a re-run is not a duplicate.
- Contracts: owner-password-only PDFs (they open without a password) are still detected as encrypted and HOLD. Conservative, matches plan 6.1.
- Contracts: `DEMO_RESET_TOKEN` shorter than 16 characters counts as unset, so `/api/reset` is refused (an empty token must never match an empty header).
- Contracts: seed, samples and fixtures are read from `<project root>/data` regardless of `DATA_DIR`; only `app.db` and `uploads/` live under `DATA_DIR`. On Railway the volume should therefore be mounted outside `/app/data` (Phase 8).
- Phase 1a (data): two parentheticals in the plan section 3 PO table are not stored in the seed. `purchase_orders.json` has no field for a PO note, so PO-1007's "(Q4 reorder)" lives only in sample 02's `_meta.setup`, and PO-1007's lines are worded exactly like PO-1001's. PO-1008's line is "Warehouse racking installation" without "(lump sum)", exactly like sample 09's invoice line in docs/CONTRACTS.md 3.2, so the per-line price check pairs them by identical wording (a lump sum is quantity 1 with unit_price = amount, as in PO-1003).
- Phase 2: with `EXTRACT_MOCK` set, a PDF that is not one of the generated samples gets a clean `document_type: "other"` extraction (every confidence 0.1) instead of an extraction failure, so it ends in the normal "not an invoice" HOLD. `EXTRACT_MOCK=fooled` applies sample #9's injected values (PO-1003 / total 400) and sets every confidence to 1.0 but keeps `suspicious_content` (the mock's first JSDoc said it clears it). Both are logged in `docs/CONTRACT_CHANGES.md`.
- Phase 2: the mock's reported latency is simulated (600-1399 ms, stable per file) and nothing actually waits; `model` is `"mock"` and cost 0 on every mock result.
- Phase 2: `scripts/eval-extract.ts` runs each model alone (its own single retry, no fallback model) so a model's own failures show, and takes a sample's `_meta.render === "scanned"` as `isImageOnly` (the stage-2 screen stands in). `--out` without a file name refuses to write `docs/eval-extract.md` from a mock run, so mock output can never overwrite the saved real comparison.
- Phase 2: nothing in `extract.ts` has run against the real OpenRouter API (no key in the build). The request shape, the strict schema with nullable type arrays and `require_parameters` are verified only against a local fake server and against docs/notes-openrouter.md; the first real `eval-extract` run is the real test (docs/CONTRACTS.md section 9 lists what stays unverified).
- Phase 1b (sample PDFs): the scanned sample (#5) is the services template rotated `rotate(0.7deg) scale(1.02)` (the plan says rotate only); the 2% zoom keeps the tilted sheet covering the whole frame so no blank wedges show at the corners. The rest is the plan's recipe (`grayscale(1) contrast(1.15) blur(0.4px)`, a faint SVG-noise overlay) shot as a 2x JPEG (quality 80) and embedded with pdf-lib; the PDF has no text layer.
- Phase 1b: the sample documents carry details the plan does not specify, none of which any rule reads: invented vendor addresses, bank names and `.example` web/e-mail domains, a fictional buyer ("Larkspur Retail Group, Inc."), dates printed in a different style per vendor, and the vendor's phone number printed as the one on file. Sample 10's balances ($15,180.00, the sum of samples 01 and 06) are decoration because its truth file has no amounts. A vendor keeps one look (font stack, colours, logo) across layouts, so #4 differs from #2 by layout, not by branding.
- Phase 1b: #9's hidden sentence is set in the page font (Trebuchet MS) and reaches pdf.js as ONE 0.75pt item, not the three items the plan's section 7 notes describe; that split at the "fi" ligature depends on the font (it happens with Helvetica Neue). The guardrail code must keep joining consecutive tiny items, which the Phase 4 Chromium fixture covers.
- Phase 4: the injection scan bounds `.*` / `.+` in every pattern to a 200-character gap (`MAX_PATTERN_GAP` in `guardrails.ts`; `config.ts` is untouched). The config pattern `/disregard .*instructions/` is quadratic on text like "disregard disregard ..." (measured: 14 ms at 20 KB, 963 ms at 160 KB, so about 40 s at 1 MB; the bounded scan needs about 6 ms at 160 KB). The cost: "disregard" and "instructions" more than 200 characters apart are no longer one hit.
- Phase 4: the scan folds text with NFKD plus dropping combining marks (a superset of the plan's NFKC), and when the text holds zero-width, format or control characters it runs twice, once with them removed ("ig<ZWSP>nore") and once as spaces ("ignore<ZWSP>all"). The screen and the grounding text put a newline between pages, so a phrase or token never glues across a page break (`joinText` itself is unchanged).
- Phase 4: `injectionHits` snippets whose context overlaps share one snippet (so sample #9's five patterns inside one sentence give one or two quotes, not five copies); at most 20 snippets of at most 200 characters. `hiddenText` keeps at most 10 runs of at most 500 characters, because the screen result is stored as the step detail and polled by the UI.
- Phase 4: "image-only" and `textChars` count visible characters only: whitespace, zero-width, format and control characters are not text. A text layer of 30 zero-width spaces is therefore image-only, not a text PDF with nothing to ground.
- Phase 4: grounding is conservative where it must guess. An identifier printed as two tokens ("INV" "0042") does not ground (whole tokens only), a European amount ("1.150,00") is not parsed, and a miss HOLDs with the plan's reason. A null or blank extracted value is `not_applicable`: a missing invoice number or total is the validate stage's finding, not a grounding miss. Amounts accept a leading `$`, euro, pound or yen sign, US thousands commas, trailing punctuation and `(1,200.00)` as negative.
- Phase 4: `validateUpload` also returns "PDF is damaged or unreadable" for a PDF with no pages, for a page count that pdf-lib (page leaves) and pdf.js (the smaller of `/Count` and the pages it can reach) disagree on (two parsers would see different pages), for a text layer over 100,000 items or 1,000,000 characters (a 3 KB file can expand into 1.5 million characters; measured), and for a parse that outlives `UPLOAD_TIMEOUT_MS` (10 s). The size and page reasons are built from the limits, so a custom limit prints "File is larger than 2.5 MB".
- Phase 4: the time bound is a timer plus checks between pages and text chunks. It cuts off async stalls (pdf-lib yields every 100 objects, so a 2.6 MB file with 60,000 objects is cut off at the deadline) and text floods, but it cannot pre-empt one synchronous pdf.js run: 8 million non-text operators in a 32 KB file blocked the event loop for about 1.7 s, and nothing in-process can stop that (the result is still rejected once that run ends, never accepted late). A truly hard bound needs the parse in a worker thread or child process; not done here (a new file outside this phase's ownership, and the bundler and deploy behaviour cannot be verified without `next build`).
- Phase 4: `getTextItems` now reads pdf.js's chunked text stream instead of `getTextContent()` (same items, same order) so limits can cut a hostile file off early. A stream has to be cancelled with an Error: without one pdf.js drops the cancel, its worker task keeps waiting for the consumer and `destroy()` hangs until the deadline (found and fixed).
- Phase 4: new fixtures in `data/fixtures/`: `owner-only.pdf` (AES-128, owner password `owner`, empty user password, so it opens without a password and is HOLD only because pdf-lib reports the encryption dictionary) and `chromium-hidden-text.pdf` (real Skia/Chromium output with white text at CSS 1px, 2px and 10px, split at the "fi" ligature).
- Phase 4: known limits kept honest in the checks: white text at normal size (the fixture's 10px = 7.5pt line) is invisible to the size rule, so its values CAN ground (the injection scan flags it; a colour check needs `getOperatorList`, Node 22+). Horizontally squeezed text (`Tz`) keeps its full reported height and is not caught either. The regex scan only knows the 13 configured phrasings; look-alike letters from other alphabets (Cyrillic "o") are not folded. Text in document metadata, annotations, form fields and attachments is not part of the page text layer, so it is neither scanned nor used for grounding.
- Phase 3: a unit price above its PO line's by up to 2% (exactly 2% included, compared in cents) is a warn/info note ("within the 2% tolerance"); more than 2% above is fail/hold ("above the 2% tolerance"). The plan table and the `checkAmounts` JSDoc say "> 2% over -> warn", but the 2% tolerance above applies to the line price as well, and a warn would approve 6 laptops at 1,500 against a 1,150 PO line just because the PO total has room. Prices below the PO's are never flagged. Invoice lines pair with PO lines by description: every word of the shorter description is in the longer one (plural "s" ignored, at least two words, or the identical single word), so different model numbers never pair. To go back to the plan's warn, change `priceFails` in `checkAmounts` (`rules.ts`); no sample is affected.
- Phase 3: vendor stage refinements. An invoice with no readable vendor name, or a name that matches two vendors in the master (`resolveVendor` returns null instead of guessing), is fail/hold (manual entry), not reject: nobody knows the vendor is unknown. Names are matched after folding accents and reading "&" as "and"; "incorporated", "limited", "corporation" and "company" count as the plan's inc, ltd, corp and co before the suffixes are stripped. A bank account printed on the invoice while the master has none on file is also a HOLD (it cannot be verified). The bank reason never repeats the invoice's account or any contact detail from the invoice (only the masked account is kept in `detail`); with no phone on file it says so.
- Phase 3: PO match is `skipped` (not applicable, never a failure) when the vendor is unknown, for a statement, receipt or other non-invoice document, and for a credit note without a printed PO; no PO is inferred for those. `po` is set only when it can feed the amounts check (found, the vendor's, open, same currency). A currency that is printed but unreadable ("¥", "dollars") is a HOLD, never silently USD; a missing currency is USD. A suggestPO answer that is NONE, not a candidate (an invented number, or a real PO of another vendor), or a throw all end as fail/hold.
- Phase 3: the exact-same-file check (stage 1) counts every earlier non-errored run, a REJECT included (same bytes, same file); the duplicate check (stage 9) ignores REJECTed and errored runs, so a rejected invoice may be resubmitted. "7 days apart" is still a soft duplicate, 8 days is a recurring pattern; an unknown invoice date on either side counts as inside the window. A soft duplicate's next action reads "check with the vendor whether this repeats <number>" (the plan's "already processed under" is kept for the hard duplicate). The "(processed ...)" date in the duplicate reason is when the original run finished (`created_at`), with "dated ..." added when the invoice date differs.
- Phase 3: an invoice that fits within 2% over the REMAINING balance is approved with a warning, so the PO can end below zero (sample 02 leaves PO-1007 at -$24.00 remaining once approved); any later invoice on that PO then fails the balance check. Nothing remaining means no tolerance at all. A tax-inclusive invoice is compared with the PO as printed (conservative: the PO is pre-tax) and its reason says so. The total stands in when no subtotal is printed, for the balance, the candidate PO filter and the soft-duplicate amount.
- Phase 3: dates. "Today" is the UTC calendar day of the injected `now` (no time-zone grace): an invoice dated tomorrow is in the future, one exactly 365 days old passes, 366 does not. A numeric date is accepted only when the numbers force the order ("28/10/2026" is day first, "10/28/2026" month first, "05/05/2026" reads the same both ways); "05/06/2026" cannot be read and HOLDs in validate. An impossible date (2026-02-30) HOLDs too; a due date before the invoice date, or one that cannot be read, is only an info warning.
- Phase 3: `decide()` also reads suspicious content from the extract step's `detail.suspicious_content` (next to `ctx.extraction`), counts a `warn` with severity reject as HOLD (only a fail can reject), and names a decisive step that has no reason text ("<stage> needs manual review"). `nextAction()` lets a security flag win even over an APPROVE handed in by mistake, and adds advice for ingest failures (unlocked copy, valid PDF, "do not process this file again") and for a unit price above the PO's (corrected invoice or PO amendment), which the plan's table does not list.
- Integration (red-team fixes): each line's own arithmetic is checked in validate: quantity x unit price must equal the line amount within the 0.02 arithmetic tolerance (a padded "2 x 1,150.00 = 2,600.00" no longer passes because the lines still add up). An invoice whose unit price is printed rounded to the cent and whose amount was computed from the unrounded price can therefore HOLD with an arithmetic reason (conservative).
- Integration: the per-line price check compares the unit price the line actually charges: amount / quantity when no price is printed, or when the amount is above quantity x printed price by more than the rounding of the amount to cents. Prices are compared exactly as a ratio (`(invoice - PO) / PO <= 2%`), never rounded to cents first, so a $0.0549 label against a $0.05 PO line (+9.8%) holds and $0.255 against $0.25 (exactly +2%) is only a note. This replaces Phase 3's "compared in cents" wording; the 2% boundary itself is unchanged.
- Integration: billed invoice lines that pair with no PO line are no longer dropped. They are listed in the amounts step (`unmatched_lines`) and HOLD when they are more than 2% of the billed lines (the same tolerance), otherwise they are an info note. A line the PO lists at $0.00 ("included") that is billed above $0 holds. The plan only describes lines that do pair; a word-based pairer that cannot pair a re-worded line now fails safe (HOLD) instead of approving it unchecked.
- Integration: tax is bounded. Validate HOLDs when tax is charged on a pre-tax amount of $0 or less, or when it is more than `CONFIG.maxTaxRate` (10%, the demo rate) of the pre-tax amount plus the 0.02 rounding tolerance (pre-tax = subtotal, else the line sum, else total - tax; minus tax when tax-inclusive). Lower tax is not flagged (it does not raise what is paid beyond the PO). `CONFIG.maxTaxRate` is new (logged in docs/CONTRACT_CHANGES.md).
- Integration: the soft-duplicate rule compares like with like: subtotals when both invoices printed one, totals when either did not, so the same $2,300 + $230 charge printed once without a subtotal line is held as a possible duplicate of the copy that has one. When both print a subtotal, the subtotals decide as before.
- Integration: vendor names fold multi-word legal forms before the suffix strip ("Limited Liability Company/Co" -> LLC, "Proprietary Limited" -> Pty Ltd, "Proprietary" -> Pty), so an approved vendor printing its full legal name is no longer routed to onboarding.
- Integration: "Manual data entry required." is the next action only when a validate problem is about reading the document (missing, unreadable, low-confidence or ungrounded values). A date out of range or the vendor's own arithmetic falls through to the PO / amounts advice or "Review the reasons above." (the plan's fallback). The validate step records `problem_kinds`; a step without it keeps the old answer.
- Integration: an over-billing reason names at most 5 approved invoices ("... and N more") and the amounts evidence keeps at most 20 numbers plus `approved_invoice_count`, because the reason becomes the dashboard's top reason.
- Integration: the pdf.js text read of `validateUpload` runs in a worker thread (`src/lib/pdf-text-worker.mjs`, plain JS loaded by path from `<root>/src/lib`) that is terminated at the upload deadline, with a 256 MB heap cap and a watchdog that stops it when the process grows by more than 256 MB. In-process, a 157 KB file of non-text operators blocked the whole event loop for 8.5 s. Text reads run one at a time on one warm worker (the pipeline is serial anyway); a read that waits keeps its own deadline. Without that queue, eight workers starting at once grew the process by ~300 MB and the watchdog rejected ordinary files (found and fixed at integration). If no worker can be started, the old in-process read is used and a warning is logged once. `getTextItems` (no limits, scripts only) stays in-process.
- Integration: the injection scan reads dash look-alikes (U+2010-2015, U+2212, U+2043, ...) as "-" and colon look-alikes (U+2236, U+A789, ...) as ":", and a text that contains invisible characters is scanned once more, with those characters removed and every space of a pattern optional, so "ig<ZWSP>nore all<ZWSP>previous instructions" is caught.

## Known limits

(Accepted at integration, 2026-11-03, after the red-team review. Each is a deliberate trade, not an open bug.)

- The injection patterns are the plan's list (section 6.2) verbatim, and three of them are broad: `override`, `\bsystem:` and `\bassistant:` also match ordinary invoice text such as "Override valve OV-200", "Operating System: Windows Server 2022" or "Assistant: Jane Roe" (red team RG-2). Such an invoice is HELD with the security flag and goes to finance security review: a false positive costs a manual review, never a wrong payment or rejection. Tightening the patterns changes the plan's detection list, so it is left to the owner; the sample texts avoid these words (docs/CONTRACTS.md 3.2).
- The scan does not fold look-alike LETTERS from other alphabets (a Cyrillic "о" in "оverride") and knows only the configured phrasings; the architecture (the model decides nothing), grounding and the model's own `suspicious_content` remain the other layers.
- The upload worker is verified under tsx on Node 20 only. Under `next build` / `next start` it relies on `<cwd>/src/lib/pdf-text-worker.mjs` existing at run time and on webpack leaving `new Worker(path)` alone; neither could be checked here (`next build` was not allowed). If the worker cannot start, uploads are parsed in-process again (logged once), which brings back the event-loop stall for hostile files.
- The memory watchdog measures the whole process (RSS), sampled every 50 ms: a burst between samples can overshoot the 256 MB cap, and unrelated growth in the same process during an upload counts against it. The pipeline is serial, so in practice one upload is parsed at a time.
- Line pairing is word-based. A real model that re-words a line (or a vendor that describes an item differently from the PO) makes that line "not on the PO", which HOLDs when it is more than 2% of the billed lines: safe, but a source of manual reviews with real invoices.
- The tax ceiling is the single 10% demo rate. Real invoices with a higher legitimate rate (for example 13% HST or 20% VAT) would HOLD; a real deployment needs per-vendor or per-jurisdiction rates.
