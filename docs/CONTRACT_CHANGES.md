## 2026-11-03 integration - src/lib/pdf.ts + new src/lib/pdf-text-worker.mjs (validateUpload's text read isolated; new exports)
- Before: `validateUpload` read the pdf.js text layer in-process (`readPdfText`).
- After: same signatures and the same results (scripts/checks/guardrails.ts compares the worker's items with `getTextItems` on every sample). The pdf.js read inside `validateUpload` runs in a worker thread started from `src/lib/pdf-text-worker.mjs` (plain JS, loaded by path: `<__dirname>` or `<cwd>/src/lib`), terminated at the deadline; heap cap `TEXT_WORKER_HEAP_MB` (256) and an RSS growth watchdog `TEXT_WORKER_MAX_GROWTH_MB` (256), both new exports. A file stopped by a cap is "PDF is damaged or unreadable" (code `damaged`, REJECT), like the other limits. Text reads are queued and run one at a time on one warm worker (unref'd, so scripts still exit); a queued read keeps its own deadline, so concurrent `validateUpload` calls still work, they just read one after another. No worker available -> the old in-process read, logged once. `getTextItems` is unchanged (in-process, no limits).
- Why: red-team finding RG-1: a 157 KB in-limit PDF of non-text operators blocked the whole event loop for 8.5 s (26.7 s for a 468 KB one) and grew the process to ~600-900 MB; the deadline timer could not fire until pdf.js finished.
- Affects: Phase 5/8: nothing to change in code; the deploy image must contain `src/lib/pdf-text-worker.mjs` and `node_modules/unpdf` at run time (a normal `next start` from the repo does). Unverified under `next build` / `next start` (not allowed in this step).

## 2026-11-04 Automations A4 and A5 - src/lib/automations/{engine,vars,send}.ts, src/app/api/reset/route.ts (the engine and the sender; reset pauses and supersedes them)
- Before: nothing ran after a decision.
- After:
  - `engine.ts`: `dispatchRunFinished(deps, runId)` queues one execution of each enabled "When an invoice is decided" automation whose outcome filter matches (idempotent per invoice by the execution's trigger key; recorded as skipped over the hourly limit); `startTestExecution` (a test ignores `enabled` and the filter and writes no note or assignment); `executeWorkflow` walks the steps in a stable topological order, records every step (status, chosen output, output of at most 16 KB, error, attempts), skips the branches not taken, and makes a failed step stop what follows it. Executions run on their own serial chain (`chainAutomation`, `automationsIdle`), separate from the pipeline's. `AutomationDeps` is injected: the clock, the sender, the allowed hosts, the base URL, the sleep, and whether the review feature exists.
  - `vars.ts`: `buildRunVars`, `buildReviewVars`, `buildSummaryVars`, built only from the names in `VARIABLES`; texts from an invoice are capped; no bank account and no raw model output.
  - `send.ts`: `sendHttps` (https on 443 only, an allow-list that is empty by default, every resolved address checked against a block list of private and reserved ranges, the connection pinned to the vetted address, a literal IP judged without lookup, no redirects, a whole-attempt deadline, at most 64 KB read), `signPayload` (HMAC-SHA256 over `timestamp.body`, headers `x-invoice-ap-timestamp` and `x-invoice-ap-signature`), `hostAllowed`, `isBlockedAddress`. Every refusal is a fixed sentence; an exception message is never kept.
  - **Reset route.** `POST /api/reset` pauses automations first (no execution is recorded meanwhile), waits for the running ones for at most `resetIdleWaitMs`, bumps a generation inside its exclusive section so an execution that was still running stops without writing, and resumes in a `finally`.
- Tests: check group `automations` (22 more tests: the seeds' routing, idempotent dispatch, skipped steps, the variables, the split by decision, test executions, the data steps, the summary, preview and live sends, the send and execution limits, retries with 1 s and 4 s sleeps, a reset during a slow send, pause and `AUTOMATIONS_ENABLED=false`, a throwing step, and the sender's allow-list, address, refusal, connection, answer and deadline cases). `test:api` still ends with "fetch was never called".
- Why: Automations plan tasks A4 and A5.
- Affects: nothing yet; the pipeline calls the engine from A6.

## 2026-11-04 Automations A12 - src/lib/automations/schedule.ts, src/instrumentation.ts (the scheduler)
- Before: nothing started an automation by itself at a set time.
- After: `schedule.ts` exports `latestSlot` (the latest scheduled slot at or before now, UTC: today or yesterday for a day schedule, this or the previous hour for an hour schedule), `dispatchSchedule` and `tickSchedules` (every enabled "On a schedule" automation whose latest slot is not before the moment it was turned on and has no execution yet gets one, with the trigger key `schedule:<slot ISO>`), and `startScheduler` (a tick now and every `automationSchedulerTickMs`, once per process, `unref`ed). Only the latest slot ever runs, so downtime causes no catch-up storm; on a host that sleeps idle instances, a slot that fell while it slept runs once on waking if it is still the latest. `register()` in `instrumentation.ts` calls `startScheduler()` after its one log line; the scheduler logs nothing, and is a no-op when `AUTOMATIONS_ENABLED=false` or `AUTOMATION_SCHEDULER=off` (the tests set the latter).
- Tests: check group `automations` (3 more: slots across a day, a month, a year and midnight; once per slot, not before it was turned on, one execution after five days of downtime, off and switched off; an hourly schedule); `test-api` group "automations" +1 (seed 3 on with a URL: two held runs in the window give one chat message starting "2 invoices on hold in the last 24 hours ($11,550.00):", and a second tick sends nothing). The instrumentation test still sees exactly one log line.

- Affects: a deployed server now checks its schedule automations once a minute.

## 2026-11-04 Automations A8 - src/app/api/automations/**, src/app/api/runs/[id]/automations, src/app/api/_lib/{automation-views,write-guard}.ts, src/lib/types.ts, src/components/shared/api.ts (nine endpoints and their types)
- Before: no HTTP surface for automations.
- After (every route is `runtime = "nodejs"`, `dynamic = "force-dynamic"`; a change needs the operator token in `x-reset-token`, then its own write limit of 30 a minute per address, then a JSON body, in that order):
  - `GET /api/automations` -> `AutomationsListResponse` (anyone).
  - `POST /api/automations` `{ name: 1..60, start: "seed:route-holds" | "seed:chat-rejections" | "seed:daily-holds" | "blank:run_finished" | "blank:schedule" }` -> `201 { id }`. The copy is off; a copy of a seed has its graph and no secrets. `400 "Send {name, start} as JSON."`.
  - `GET /api/automations/:id` -> `AutomationDetail` (the graph, `secrets` as `{ has_url, url_hint, has_signing_secret }` per sending step, the problems found, `sending_enabled`, `allowed_hosts`, `review_trigger_available`); `404 "Automation not found."`.
  - `PUT /api/automations/:id` `{ name, graph, version, secrets?: { [nodeId]: { url?: string | null, signing_secret?: string | null } } }` -> `200 { version, problems, turned_off }`. Secrets are merged before validation (an absent key keeps, null clears, a URL must be `https://…` of at most 2,000 characters, a signing secret 1 to 200), the secrets of steps that no longer exist or never send are dropped. A save of an enabled automation with problems still saves, turns it off (`turned_off: true`) and returns the problems. `409 "Someone else saved this automation. Reload to see their changes."` for a stale `version`; `400` for an unreadable graph or a bad URL; `413 "This automation is too large."` over 128 KB. `turned_off` is an addition to the plan's `{ version, problems }`.
  - `POST /api/automations/:id/enabled` `{ enabled }` -> `200 { enabled }`; turning on with problems is `409 { error: "Fix the problems listed before turning this automation on.", problems }`.
  - `DELETE /api/automations/:id` -> `200 { ok: true }` (its executions go; notes and assignments stay).
  - `POST /api/automations/:id/test` `{ run_id: uuid | null, send: boolean }` -> `202 { executionId }`, or the engine's refusal (`400 "Choose a finished invoice to test with."`, `409 "Fix the problems listed before testing."`, `404`).
  - `GET /api/automations/:id/executions?limit=1..100` (default 25) -> `{ executions: ExecutionListItem[] }`; `GET /api/automations/executions/:executionId` -> `ExecutionDetail` (steps and the graph the execution ran); `GET /api/runs/:id/automations` -> `RunAutomationsResponse` (executions, notes, the assignment, `pending`).
  - **Secrets never leave.** No response contains a webhook URL or a signing secret, only the hint (`hooks.slack.com/…/a1b2`); a test asserts it for the detail, the list and the save's own answer.
  - **Client.** `components/shared/api.ts` gained `getAutomations`, `getAutomation`, `createAutomation`, `saveAutomation`, `setAutomationEnabled`, `deleteAutomation`, `testAutomation`, `getExecutions`, `getExecution`, `getRunAutomations` (writes send the token and use a 30 s timeout).
- Tests: `scripts/test-api.ts` group "automations" (12 more: the list and the seeds' problems, the token on every change, create, versioned saves, cycle and turn-off, secrets never returned, the two routed samples, executions and their detail, a test with a preview and the refused real send, delete, the write limit, recovery on a real file); `scripts/smoke-http.ts` +3.
- Why: Automations plan task A8.
- Affects: nobody (no page uses them yet).
