## 2026-11-03 integration - src/lib/pdf.ts + new src/lib/pdf-text-worker.mjs (validateUpload's text read isolated; new exports)
- Before: `validateUpload` read the pdf.js text layer in-process (`readPdfText`).
- After: same signatures and the same results (scripts/checks/guardrails.ts compares the worker's items with `getTextItems` on every sample). The pdf.js read inside `validateUpload` runs in a worker thread started from `src/lib/pdf-text-worker.mjs` (plain JS, loaded by path: `<__dirname>` or `<cwd>/src/lib`), terminated at the deadline; heap cap `TEXT_WORKER_HEAP_MB` (256) and an RSS growth watchdog `TEXT_WORKER_MAX_GROWTH_MB` (256), both new exports. A file stopped by a cap is "PDF is damaged or unreadable" (code `damaged`, REJECT), like the other limits. Text reads are queued and run one at a time on one warm worker (unref'd, so scripts still exit); a queued read keeps its own deadline, so concurrent `validateUpload` calls still work, they just read one after another. No worker available -> the old in-process read, logged once. `getTextItems` is unchanged (in-process, no limits).
- Why: red-team finding RG-1: a 157 KB in-limit PDF of non-text operators blocked the whole event loop for 8.5 s (26.7 s for a 468 KB one) and grew the process to ~600-900 MB; the deadline timer could not fire until pdf.js finished.
- Affects: Phase 5/8: nothing to change in code; the deploy image must contain `src/lib/pdf-text-worker.mjs` and `node_modules/unpdf` at run time (a normal `next start` from the repo does). Unverified under `next build` / `next start` (not allowed in this step).

## 2026-11-03 fix round 2 (re-review) - src/lib/ratelimit.ts, src/lib/config.ts, src/app/api/_lib/http.ts, src/app/api/_lib/uploads.ts and POST /api/runs (security SEC-6: uploads that stall or crawl)
- Before: POST /api/runs recorded its `MAX_RUNS_PER_HOUR` slot at the door (`checkRateLimit(ip, at)`) and gave it back when the request ended without a 202. The body read had no deadline (Node's 300 s request timeout ended a stalled upload), and any number of uploads could be in progress at once. 60 uploads that sent one part header and stopped (6 addresses x 10) held all 60 hourly slots and 60 temp files, and an honest POST got 429 "Try again in 60 min" while no run existed.
- After (every existing call still compiles and behaves as before; everything is additive):
  - `src/lib/ratelimit.ts`: `checkRateLimit(ip, now?, opts?: RateLimitOptions)` with `interface RateLimitOptions { recordGlobal?: boolean }`. The default (true) is the old behaviour; with false the hourly cap is checked but no slot is taken (the per-address call is still recorded). New `takeGlobalSlot(now?): RateLimitResult` takes one hourly slot if one is free, checking the cap again; a refusal is worded like `checkRateLimit`'s hourly refusal (scope "global", the truthful wait) and records nothing, and `refundGlobalSlot(at)` gives a taken slot back. New `interface UploadSlot extends RateLimitResult { release(): void }` and `beginUpload(ip): UploadSlot`: uploads in progress are capped per address (the limiter's buckets: IPv6 per /64, IPv4-mapped as IPv4, a port ignored) and in all; a refusal has scope "ip" or "global", `retryAfterSec` = `CONFIG.uploadsBusyRetryAfterSec`, and records nothing; `release()` is idempotent. New `uploadsInFlight(): { total: number; ips: number }` (tests). `resetRateLimits()` does not clear uploads in progress.
  - `src/lib/config.ts`: new `CONFIG.bodyReceiveTimeoutMs` (60000), `CONFIG.maxUploadsInFlightPerIp` (2), `CONFIG.maxUploadsInFlight` (16) and `CONFIG.uploadsBusyRetryAfterSec` (5). Every existing key and value is unchanged.
  - `src/app/api/_lib/http.ts`: new `bodyDeadline(reader, ms)` and `type BodyFailure = "too_large" | "timeout"`; `readBody(req, maxBytes, timeoutMs = CONFIG.bodyReceiveTimeoutMs)`, whose failure variant now carries `reason`. `src/app/api/_lib/uploads.ts`: `spoolBody(req, maxBytes, timeoutMs = CONFIG.bodyReceiveTimeoutMs)`, whose failure variant carries `reason`; the temp file is removed on a timeout as on a 413.
  - POST /api/runs, in this order. (1) A multipart upload needs a place among the uploads in progress, else 429 with `Retry-After: 5`, its body never read and nothing counted. (2) The rate limit, before the body is read: the per-address minute is recorded and the hourly cap only read, so a full hour is still a 429 at the door. (3) The body must arrive whole within `CONFIG.bodyReceiveTimeoutMs`, JSON or multipart, else 408 with a fixed message and the temp file removed. (4) The hourly slot is taken with `takeGlobalSlot` once the body is complete, right before the file is stored and `createRun` runs; 429 if the hour filled up meanwhile. The slot is given back unless the request answers 202.
- Why: re-review finding security-SEC-6, deferred in the previous round. Taking the slot only once the body is complete was chosen over keeping the old accounting with a deadline: with the old accounting every stalled body still holds a slot for up to the 60 s deadline (a mutation test measured 14 slots held by 12 stalled uploads and one stalled JSON body), JSON bodies are not covered by the upload cap, a lower `MAX_RUNS_PER_HOUR` lets the stalls fill the hour, and the 429 would say "Try again in 60 min" for slots that free up within a minute.
- Tests: six new tests in `scripts/test-api.ts`, all named "fix round SEC-6: ..." (2 in the ratelimit group, 4 in routes); each fails against the previous code. Every earlier test is unchanged; the `withConfig` helper also accepts `bodyReceiveTimeoutMs`. Checked under `next start` too (prove stage, loopback): the third concurrent upload from one address got 429 at once, an honest sample run from another address got 202 while uploads stalled, and each stalled or crawling client received the complete 408 at 60 s.
- Affects: nobody has to adapt. The start page shows a 408's message like any other 4xx; it words a 429 from the upload cap like a rate-limit 429 ("Too many runs were started in a short time", with the right wait).
